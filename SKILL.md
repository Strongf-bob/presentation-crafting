# Presentation Crafting

## Overview

Презентация начинается не со слайдов, а с понимания цели и целевой аудитории. Каждая презентация живёт в собственной папке и состоит из четырёх артефактов, создаваемых строго в порядке:

```
01-brief.md (зачем + ЦА + стиль + структура)
        ↓
02-deck-spec.md (структура + каждый слайд с точным текстом и ссылками на картинки)
        ↓
assets/ (вложения, которые попадают на слайды)
        ↓
deck.html / deck.pptx / deck.pdf (сама презентация)
```

**Не начинать работу, пока база (бриф) не собрана и не одобрена пользователем.**

Скилл самодостаточен: для сборки `deck.html` достаточно `references/html-deck.md`, внешние скиллы не требуются. Для малых внутренних дек (≤5 слайдов) — lite-режим (см. ниже).

## When to Use

- Создание любой презентации/деки/питча под конкретную аудиторию
- Защита проекта, выступление на конференции, продажа клиенту, отчёт руководству
- When NOT to use: обычные документы без слайдов, UI-дизайн, README, code review

## Core Workflow (обязательный порядок)

1. **Preflight (сбор базы)** — задать обязательные вопросы: цель, ЦА, регламент, материалы, формат. Производные параметры (стиль, плотность, дизайн vs текст) вывести по таблице ситуаций и зафиксировать в брифе. Пока базы нет — не делать папку, не писать слайды. Малые внутренние деки (≤5 слайдов) — по lite-режиму (см. ниже).
2. **Папка** — создать `presentations/<deck-name>/` в текущей рабочей директории. Если cwd — не проект (домашняя директория и т.п.), спросить, где создать. Всю работу вести только внутри этой папки.
3. **Ресерч (фактура)** — по `references/research.md`: прочитать вложения, исследовать кодовую базу (если презентация о проекте — писать только правду о том, как она работает), при необходимости веб. Только подтверждённые факты с источниками идут в бриф.
4. **Бриф** — `01-brief.md` по шаблону `templates/brief.md`. Показать пользователю, получить одобрение. Без одобренного брифа слайды не начинать.
5. **Спек** — `02-deck-spec.md` по шаблону `templates/deck-spec.md`: сначала структура презентации, потом каждый слайд (тип, цель, заголовок, точный текст, источники цифр, изображения из `assets/`, акцент, заметки докладчика). Пример заполнения — `examples/deck-spec-example.md`.
6. **Ассеты** — положить вложения в `assets/`, проверить, что все пути из спека существуют.
7. **Презентация** — собрать презентацию по `references/html-deck.md` (по умолчанию self-contained HTML; PPTX/PDF — если договорились, пути сборки там же). Визуальные правила — `references/slide-design.md`.
8. **Верификация** — пройти чек-лист ниже, только потом показывать как готовое.
9. **Фактчекинг** — два обязательных захода перед объявлением «всё готово» (см. раздел Fact-Checking).

## Preflight (достаточная база)

### Обязательные вопросы (спросить, если ответа нет в запросе)

1. **Цель** — зачем эта презентация? Какое действие/решение должно последовать после неё?
2. **ЦА** — кто именно будет смотреть? Роль, уровень погружения в тему, ожидаемые возражения и вопросы?
3. **Регламент** — сколько минут на выступление? (из этого выводится число слайдов: 1–2 мин/слайд)
4. **Материалы** — есть ли вложения (картинки, данные, документы), которые обязаны попасть в презентацию? Есть ли брендбук / корпоративный шаблон?
5. **Формат** — HTML/PPTX/PDF? Живое выступление или чтение с экрана?

### Производные параметры (не спрашивать, а вывести)

Стиль оформления, плотность текста, «дизайн vs текст» — выводятся из таблицы ситуаций (`references/audience-structures.md`) по ЦА и формату подачи, фиксируются в брифе и подтверждаются при его одобрении. Пользователю эти вопросы напрямую не задавать — он на них обычно не может ответить содержательно.

Если ответов на обязательные вопросы нет — задать вопросы, не начинать. Если пользователь говорит «на твоё усмотрение» — выбрать параметры по таблице структур (`references/audience-structures.md`), явно зафиксировать допущения в брифе и получить одобрение брифа.

## Lite-режим (малые деки)

Если дека ≤5 слайдов и аудитория внутренняя (команда, статус, синк):

- вместо отдельного брифа — блок «Бриф (сжатый)» в начале `02-deck-spec.md`: цель, ЦА, формат подачи, регламент, выбранная структура — 5–7 строк;
- отдельный раунд одобрения брифа не нужен — спек показывается пользователю как обычно;
- папка, ассеты, верификация и фактчекинг — без изменений, они обязательны и в lite-режиме.

Полный церемониал на трёх внутренних слайдах — антипаттерн; отсутствие брифа вообще — тоже.

## Folder Structure

```
presentations/<deck-name>/
├── 01-brief.md        # понимание: зачем, ЦА, стиль, выбранная структура + обоснование
├── 02-deck-spec.md    # структура + каждый слайд (текст, картинки, акценты)
├── assets/            # вложения, которые идут на слайды
└── deck.html          # сама презентация (или deck.pptx / deck.pdf)
```

- Если папки `presentations/` ещё нет — создать. По умолчанию — в текущей рабочей директории; если cwd — не проект (домашняя директория и т.п.), спросить пользователя, где создать, а не мусорить в чужом репозитории.
- `<deck-name>` — короткое имя в kebab-case (например `investor-pitch-2026`).
- Всю работу вести только внутри папки презентации: файлы не должны валяться в корне проекта.

## Artifacts

### 1. Бриф (`01-brief.md`)

Шаблон: `templates/brief.md`. Обязательные поля: цель, ЦА, стиль, дизайн vs текст, плотность текста, выбранная структура с обоснованием (почему именно эта структура под эту ЦА), материалы. Бриф — источник истины: если позже возникнут сомнения, возвращаться к брифу.

### 2. Спек (`02-deck-spec.md`)

Шаблон: `templates/deck-spec.md`. Пример заполнения: `examples/deck-spec-example.md`. Сначала — структура презентации (номера и названия слайдов). Затем для каждого слайда:

- цель слайда
- заголовок (несёт вывод)
- точный текст, который будет на слайде (дословно)
- источники — откуда каждая цифра и факт (файл из `assets/`, данные пользователя, документ; оценки помечаются «оценка»). Указывать при написании спека, не искать задним числом на фактчекинге
- изображения — ссылками на `assets/` (что за картинка, зачем, где на слайде)
- акцент (что приковывает внимание)
- заметки докладчика (что говорить)

Изображения ссылать на `assets/` относительными путями — никаких внешних URL без проверки.

### 3. Ассеты (`assets/`)

Вложения, которые попадают на слайды. Именовать kebab-case. Файлы, нужные только для справки (не на слайды), в `assets/` не класть. Сгенерированные для слайдов изображения и диаграммы — тоже в `assets/`, kebab-case; в спеке указать происхождение (сгенерировано, по каким данным).

### 4. Презентация

По умолчанию — self-contained HTML по `references/html-deck.md` (формат файла, токены, навигация, чарты, валидация). Визуальные правила (типографика, цвет, сетка, типы слайдов, анти-слоп) — `references/slide-design.md`. Скилл `design-system` — опционально: если установлен, можно брать из него токены и валидацию слайдов, но он **не требуется**. PPTX (python-pptx) и PDF (печать из HTML) — только если согласовано в брифе, пути сборки описаны в `references/html-deck.md`. Слайды должны быть legible / simple / obvious по YC (см. `references/audience-structures.md`).

## Выбор структуры под ЦА

Структура выбирается по целевой аудитории — это отдельный справочник: **`references/audience-structures.md`** (обязателен к чтению до выбора структуры). Там: система из 6 архетипов по цели (информировать / убедить / защитить / обучить / отчитаться / вдохновить), таблица ситуаций → архетип → параметры, шкала плотности текста, ось «живое выступление / чтение с экрана», вывод числа слайдов из регламента, YC Seed (10 вопросов), YC Series A (traction-first), 12-слайдовая структура, академические структуры (диплом, кейс, хакатон, конференция), «9 блоков» с картой «блок ↔ возражение аудитории», дизайн-принципы YC.

Выбор фиксировать в брифе с обоснованием: «архетип = X, структура = Y, потому что ЦА = ... и им важно ...».

## Изменения после одобрения

После одобрения брифа ничего не правится напрямую в `deck.html`. Изменения идут цепочкой:

- структурные (состав/порядок слайдов, структура, ЦА) → обновить бриф → обновить спек → перегенерировать затронутые слайды;
- точечные (текст, цифра, картинка на слайде) → обновить спек → перегенерировать слайд.

Бриф остаётся источником истины: если дека разошлась с брифом, неправильна дека, а не бриф.

## Fact-Checking (обязателен перед «всё готово»)

Два захода, оба обязательны. Пропустить нельзя, «на глаз нормально» не считается.

### Заход 1: источник истины

Проверить, что каждая цифра и каждое утверждение на слайдах сводятся к единому источнику правды (бриф, материалы в `assets/`, данные от пользователя):

- у каждой цифры есть конкретный источник (файл, документ, данные пользователя) — цифр «из головы» нет
- если источник не найден — цифру убрать или запросить у пользователя, но не оставлять без источника
- все повторяющиеся цифры (одна и та же метрика на разных слайдах) пересчитать — значения должны совпадать везде
- утверждения без источников (доли, тренды, «в 3 раза быстрее») либо подкреплены, либо помечены как оценка

### Заход 2: глазами члена борда

Прочитать презентацию так, как её прочитает человек, у которого нет ничего, кроме самой деки:

- текст не противоречит сам себе (слайд 3 против слайда 7, цифры в заголовке против цифр на графике)
- нет утверждений, опирающихся на контекст, которого у читателя нет: «как мы обсуждали», «в прошлом квартале», «наш партнёр» — всё, что упомянуто, либо объяснено в деке, либо вынесено в заметки докладчика
- каждая идея опирается на то, что уже сказано в деке, а не на знания докладчика
- выводы следуют из данных, показанных на слайдах, а не подразумеваются

Результат фактчекинга — финальный список найденных проблем и их исправление. Только после этого презентация может называться готовой.

## Verification

- [ ] Бриф одобрен пользователем до генерации слайдов (в lite-режиме — сжатый бриф есть в начале спека)
- [ ] Папка `presentations/<deck-name>/` создана, ничего не лежит в корне проекта
- [ ] Ресерч проведён: факты о проекте/продукте подтверждены (код, документы, данные) — выдуманных фич и цифр нет
- [ ] Ghost deck test: заголовки слайдов, прочитанные подряд, рассказывают всю историю
- [ ] В спеке каждый слайд: тип указан, одна идея, заголовок несёт вывод
- [ ] Текст на слайде = текст из спека, ничего лишнего
- [ ] У каждой ключевой цифры в спеке указан источник
- [ ] Каждая картинка из спека существует в `assets/`
- [ ] Плотность текста соответствует брифу и формату подачи (живое выступление / чтение с экрана)
- [ ] Лимиты типов слайдов соблюдены, тело ≥ 18pt (`references/slide-design.md`)
- [ ] Дизайн без анти-слоп паттернов: ≤2 шрифтов, ≤3 цветов, контраст по WCAG, нет wall of text (`references/slide-design.md`)
- [ ] Дека пройдена в браузере от первого слайда до последнего: навигация работает, ничего не вылезает за слайд (по `references/html-deck.md`)
- [ ] Фактчекинг, заход 1: каждая цифра → конкретный источник, нет цифр «из головы», повторы сходятся
- [ ] Фактчекинг, заход 2: дека прочитана глазами члена борда — нет внутренних противоречий и опоры на неявный контекст

## Common Mistakes

| Ошибка | Как правильно |
|---|---|
| Начать слайды без брифа | Всегда бриф → одобрение → спек → слайды |
| Полный церемониал для 3 внутренних слайдов | Lite-режим: сжатый бриф блоком в начале спека |
| Выдуманные фичи и цифры продукта | Ресерч кодовой базы/материалов; на слайдах — только подтверждённое |
| Файлы в корне проекта | Всё в `presentations/<deck-name>/` |
| Структура «по ощущению» | Структура по ЦА из справочника + обоснование в брифе |
| Заголовки-этикетки («Результаты», «Методология») | Заголовок = вывод; ghost deck test по всем заголовкам |
| Один слайд = 3+ идеи | Одна идея на слайд, остальное — в отдельные слайды |
| AI slop: фиолетовый градиент, Inter, стена текста | Правила `references/slide-design.md` + лимиты по типам слайдов |
| Картинки со ссылками в никуда | Проверить пути в `assets/` |
| Источники цифр ищутся на фактчекинге | Поле «Источники» заполняется при написании спека |
| Правки прямо в `deck.html` мимо брифа | Изменения цепочкой: бриф/спек → перегенерация слайдов |
