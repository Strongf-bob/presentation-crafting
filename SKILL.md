# Presentation Crafting

## Overview

Презентация начинается не со слайдов, а с понимания цели и целевой аудитории. Каждая презентация живёт в собственной папке и состоит из четырёх артефактов, создаваемых строго в порядке:

```
01-brief.md (зачем + ЦА + стиль + структура)
        ↓
02-deck-spec.md (структура + каждый слайд с точным текстом и ссылками на картинки)
        ↓
assets/ (вложения, которые попадают на слайды)
        ↓
deck.html / deck.pptx / deck.pdf (сама презентация)
```

**Не начинать работу, пока база (бриф) не собрана и не одобрена пользователем.**

## When to Use

- Создание любой презентации/деки/питча под конкретную аудиторию
- Защита проекта, выступление на конференции, продажа клиенту, отчёт руководству
- When NOT to use: обычные документы без слайдов, UI-дизайн, README, code review

## Core Workflow (обязательный порядок)

1. **Preflight (сбор базы)** — задать вопросы, пока не станут ясны: цель, ЦА, стиль, плотность текста, вложения, формат вывода. Минимум базы — в разделе Preflight ниже. Пока базы нет — не делать папку, не писать слайды.
2. **Папка** — создать `presentations/<deck-name>/` (в текущем проекте или в рабочей директории). Всю работу вести только внутри этой папки.
3. **Бриф** — `01-brief.md` по шаблону `templates/brief.md`. Показать пользователю, получить одобрение. Без одобренного брифа слайды не начинать.
4. **Спек** — `02-deck-spec.md` по шаблону `templates/deck-spec.md`: сначала структура презентации, потом каждый слайд (цель, заголовок, точный текст, изображения из `assets/`, акцент, заметки докладчика).
5. **Ассеты** — положить вложения в `assets/`, проверить, что все пути из спека существуют.
6. **Презентация** — собрать презентацию (по умолчанию self-contained HTML; PPTX/PDF — если договорились).
7. **Верификация** — пройти чек-лист ниже, только потом показывать как готовое.

## Preflight (достаточная база)

Перед началом работы ответы минимум на эти вопросы (спрашивать у пользователя, если их нет в запросе):

1. **Цель** — зачем эта презентация? Какое действие/решение должно последовать после неё?
2. **ЦА** — кто именно будет смотреть? Роль, уровень погружения в тему, ожидаемые возражения и вопросы?
3. **Стиль** — какой стиль оформления? Что важнее для этой аудитории — дизайн или текст?
4. **Плотность текста** — сколько текста допустимо на слайд под эту аудиторию?
5. **Материалы** — есть ли вложения (картинки, данные, документы), которые обязаны попасть в презентацию?
6. **Формат** — HTML/PPTX/PDF? Живое выступление или чтение с экрана?

Если ответов нет — задать вопросы, не начинать. Если пользователь говорит «на твоё усмотрение» — выбрать параметры по таблице структур (`references/audience-structures.md`), явно зафиксировать допущения в брифе и получить одобрение брифа.

## Folder Structure

```
presentations/<deck-name>/
├── 01-brief.md        # понимание: зачем, ЦА, стиль, выбранная структура + обоснование
├── 02-deck-spec.md    # структура + каждый слайд (текст, картинки, акценты)
├── assets/            # вложения, которые идут на слайды
└── deck.html          # сама презентация (или deck.pptx / deck.pdf)
```

- Если папки `presentations/` ещё нет — создать.
- `<deck-name>` — короткое имя в kebab-case (например `investor-pitch-2026`).
- Всю работу вести только внутри папки презентации: файлы не должны валяться в корне проекта.

## Artifacts

### 1. Бриф (`01-brief.md`)

Шаблон: `templates/brief.md`. Обязательные поля: цель, ЦА, стиль, дизайн vs текст, плотность текста, выбранная структура с обоснованием (почему именно эта структура под эту ЦА), материалы. Бриф — источник истины: если позже возникнут сомнения, возвращаться к брифу.

### 2. Спек (`02-deck-spec.md`)

Шаблон: `templates/deck-spec.md`. Сначала — структура презентации (номера и названия слайдов). Затем для каждого слайда:

- цель слайда
- заголовок
- точный текст, который будет на слайде (дословно)
- изображения — ссылками на `assets/` (что за картинка, зачем, где на слайде)
- акцент (что приковывает внимание)
- заметки докладчика (что говорить)

Изображения ссылать на `assets/` относительными путями — никаких внешних URL без проверки.

### 3. Ассеты (`assets/`)

Вложения, которые попадают на слайды. Именовать kebab-case. Файлы, нужные только для справки (не на слайды), в `assets/` не класть.

### 4. Презентация

По умолчанию — self-contained HTML (навигация, адаптивность). PPTX/PDF — только если так договорились в брифе. Для генерации слайдов использовать **REQUIRED SUB-SKILL:** `design-system` (дизайн-токены, Chart.js, анимации, валидация слайдов). Слайды должны быть legible / simple / obvious по YC (см. `references/audience-structures.md`).

## Выбор структуры под ЦА

Структура выбирается по целевой аудитории — это отдельный справочник: **`references/audience-structures.md`** (обязателен к чтению до выбора структуры). Там: таблица ЦА → параметры, YC Seed (10 вопросов), YC Series A (traction-first), 12-слайдовая структура, дизайн-принципы YC, структура «9 блоков» с картой «блок ↔ возражение аудитории».

Выбор структуры фиксировать в брифе с обоснованием: «структура X, потому что ЦА = ... и им важно ...».

## Verification

- [ ] Бриф одобрен пользователем до генерации слайдов
- [ ] Папка `presentations/<deck-name>/` создана, ничего не лежит в корне проекта
- [ ] В спеке каждый слайд: одна идея, заголовок несёт вывод
- [ ] Текст на слайде = текст из спека, ничего лишнего
- [ ] Каждая картинка из спека существует в `assets/`
- [ ] Плотность текста соответствует брифу (под эту ЦА)
- [ ] Презентация открывается, навигация работает, ничего не вылезает за слайд

## Common Mistakes

| Ошибка | Как правильно |
|---|---|
| Начать слайды без брифа | Всегда бриф → одобрение → спек → слайды |
| Файлы в корне проекта | Всё в `presentations/<deck-name>/` |
| Структура «по ощущению» | Структура по ЦА из справочника + обоснование в брифе |
| Один слайд = 3+ идеи | Одна идея на слайд, остальное — в отдельные слайды |
| Картинки со ссылками в никуда | Проверить пути в `assets/` |
| Слайды после брифа меняются сами собой | Бриф — источник истины, изменения только через него |
